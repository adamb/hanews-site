ESP32 projects worth building for Home Assistant (2026)

HA News · 11 Nov 2026

An ESP32 dev board plus ESPHome is the cheapest way to add a genuinely useful sensor or control to Home Assistant. Nothing here needs a vendor cloud account: ESPHome nodes speak to Home Assistant over the local ESPHome API, and everything you build stays on your network. The projects below are ordered roughly from easiest to hardest, with the hardware each one needs and the gotchas the ESPHome documentation itself flags.

If Home Assistant runs on a Docker install or a small server you already own, you have everything required: flash the board once from a browser or the ESPHome add-on, and the node shows up in Home Assistant as entities. Reconfigure later by editing the YAML and re-flashing over Wi-Fi.

How we ranked difficulty

Difficulty here means how much can go wrong, not how clever the YAML is. A Bluetooth proxy is a one-component config and fails harmlessly. A garage door controller moves something heavy, so it sits last and deserves the most care. Cost is deliberately left out: boards and sensor module prices move around too much to quote, and every build here is the price of dinner for two or less.

1. Bluetooth proxy — easiest, most leverage

Difficulty: beginner · Hardware: any ESP32 board · Docs: ESPHome bluetooth_proxy

Home Assistant's Bluetooth integrations — including BTHome sensors and many plant and temperature sensors — only hear what their adapter can reach. The bluetooth_proxy component turns an ESP32 into a remote ear on your Wi-Fi, and Home Assistant aggregates proxies automatically alongside any USB adapter.

The limits are in the docs, not marketing: proxies handle BLE only, and each active GATT connection slot costs about 1 KB of RAM. An ESP32 defaults to 3 slots, allows up to 9 with 5 recommended, and Ethernet-based proxies handle 4 slots well. RP2040 and RP2350 boards default to and max out at 3. The proxy requires the platform's BLE tracker to be enabled in the config. If your use is "more plant sensors in the far rooms," this is the build — no soldering, no external sensors, two lines of YAML.

2. CO2 and air-quality monitor

Difficulty: beginner-plus · Hardware: Sensirion SCD30 module · Docs: ESPHome SCD30

The SCD30 is the well-documented default for CO2: an NDIR sensor on I2C at address 0x61 that reports CO2 from 0–4,000 ppm plus temperature and humidity in the same package. In ESPHome the sensor: platform: scd30 block gives you co2, temperature and humidity entities, with options for temperature_offset, automatic_self_calibration (on by default), ambient_pressure_compensation, altitude_compensation, and an update interval from 2 to 1,800 seconds (default 60).

Two details worth wiring up from the start. First, the sensor's manual recalibration is exposed to Home Assistant through the scd30.force_recalibration_with_reference action — pair it with a template button and a number helper between 350 and 4,500 ppm and you can recalibrate from the dashboard against fresh outdoor air. Second, the docs note self-calibration assumes the room sees fresh air periodically; in a permanently sealed office, disable it and recalibrate manually instead.

3. Temperature, pressure and humidity — the BME280 fallback

Difficulty: beginner · Hardware: Bosch BME280 module · Docs: ESPHome BME280

If CO2 is a nice-to-have, the BME280 is the build every house eventually gets several of. One module does temperature, pressure and humidity over I2C (address 0x77 or 0x76) or SPI, and GY-BME280 boards are common and cheap. ESPHome's platform runs measurements in forced mode with 16× oversampling by default and a 60-second interval, which is plenty for a room sensor.

This is the ideal first flashing project: wires, an I2C address, three sensors, done. Put one in every room before you attempt anything with relays or radios.

4. Addressable LED strip

Difficulty: beginner-plus · Hardware: WS2812-type addressable strip · Docs: ESPHome light core

ESPHome's addressable light platform drives WS2812-type strips directly from the ESP32, with the full light-effects library and brightness, color and effect controls showing up in Home Assistant as a light entity. The light core docs are the reference for strip setup and effects.

If you are reusing older YAML, note that ESPHome 2026.10.0 replaced the light restore_mode option with restore_state, a breaking change, so check the release notes before you update. Power injection is the classic hardware gotcha on long runs — plan for it before you staple the strip up.

5. E-paper dashboard

Difficulty: intermediate · Hardware: Waveshare or Good Display e-paper panel · Docs: ESPHome waveshare_epaper

An e-paper panel on the wall is the closest thing Home Assistant has to a printed status page: sensor values, calendar, laundry state, rendered by the ESP32 itself and refreshed only when something changes. The waveshare_epaper display platform supports a long list of panels over 4-wire SPI — the 2.90 in, 2.13 in TTGO variants including the -b73/-b1, the 1.54 in Good Display gdew0154m09 used in the M5Stack Core Ink, the 4.2 in GDEY042T81, and others, up to 7-color ACeP displays.

Pinning is the part people stumble on: CLK and DIN go on the SPI clk_pin and mosi_pin, plus CS, DC, and optionally BUSY and RESET. The full_update_every: 30 option controls partial refresh — 30 partial refreshes between full ones, which keeps ghosting manageable. Because the panel only draws when told, the whole thing can run on attention-sipping power budgets no LCD would survive.

6. mmWave presence detection

Difficulty: intermediate · Hardware: Hi-Link LD2410/LD2410B/LD2410C · Docs: ESPHome LD2410

A 24 GHz mmWave sensor solves the problem PIR never will: detecting a person who is sitting still. The Hi-Link LD2410 family reads out over UART (parity NONE, 1 stop bit; the sensor defaults to 256,000 baud, and ESPHome recommends hardware UART pins), and reports three binary sensors — has_target, has_moving_target, has_still_target — plus light level, moving and still distances, per-target energy, detection distance and per-gate energies.

One config line is essential: the platform sets a default settle: 1000ms filter on the binary sensors to avoid flooding Home Assistant with rapid on/off flapping. Leave it, though you can tune it. Placement matters more than configuration with mmWave — the sensor sees through drywall only weakly, but it does see fans, curtains and pets, so expect some tuning of gates before it behaves.

7. Garage or roller door controller — do it last

Difficulty: advanced · Hardware: dry-contact door sensor(s) plus a relay board · Docs: ESPHome template cover

ESPHome needs no special controller for a garage door: a dry-contact sensor to read the door's state and a relay board to press the wall-button circuit. The template cover platform ties them together — open_action and close_action fire your relay switches, an optional stop_action for motors that support it, and a lambda reporting state via COVER_OPEN/COVER_CLOSED. With has_position and tilt_lambda you can even expose partial-open positions. The result appears in Home Assistant as a cover entity automatically.

This build ranks last on purpose. A misconfigured cover is the one ESP32 project that can trap a car — or a person. Use opto-isolated relay boards, verify the door state sensor reads correctly before wiring the relay, and keep the physical wall button as the fallback. If the door matters to your day, test every failure mode with the door in view.

Wi-Fi config every ESP32 build shares

Whatever the sensor, the wifi component config is the same. The docs recommend a static IP for fast reconnection — worth doing in a house with dozens of nodes. The fallback AP mode kicks in after ap_timeout (default 90 seconds) if the board can't reach your network, giving you a direct Wi-Fi hotspot to fix things from. Credentials go in a secrets.yaml referenced with !secret, so the same YAML can be shared or committed without leaking passwords. On ESP32 you can even combine Ethernet and Wi-Fi via the network priority list, which matters for proxies and controllers that must never drop off.

Where to start

The honest recommendation: flash a Bluetooth proxy and a BME280 room sensor first, because both are forgiving and immediately useful. Add the SCD30 where people actually sit. Leave mmWave and e-paper for a weekend with a breadboard. The garage door is worth doing, but do it when you can watch the door while you test — and check the ESPHome guide for the flashing basics before you start.

FAQ

Do ESP32 projects work with Home Assistant without a cloud account?

Yes. ESPHome nodes talk to Home Assistant over the local ESPHome API, so sensors and controls work entirely on your network with no vendor cloud account.

How hard is each ESP32 project for a beginner?

Easiest to hardest: Bluetooth proxy, CO2 monitor, weather sensor, LED strip, e-paper dashboard, mmWave presence, and garage door last because a misconfigured cover controls something heavy and safety-critical.

Can an ESP32 run the Home Assistant Bluetooth proxy?

Yes. ESPHome's bluetooth_proxy component turns an ESP32 into a Bluetooth extension for Home Assistant. It handles BLE only, with 3 active GATT connection slots by default on ESP32, up to 9 (5 recommended).

Which CO2 sensor should I use with ESPHome?

The Sensirion SCD30 is the well-documented default: an I2C NDIR module at address 0x61 that also reports temperature and humidity, with automatic self-calibration on by default in ESPHome.

Do mmWave presence sensors replace PIR in Home Assistant?

The Hi-Link LD2410 detects still and moving targets and reports distance over UART, so it can detect a person sitting still where a PIR would time out. ESPHome exposes it as binary sensors and sensors.

Can ESPHome drive multi-color e-paper displays?

Yes. The waveshare_epaper display platform supports many Waveshare and Good Display panels over SPI, including 7-color ACeP models.

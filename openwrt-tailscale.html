Tailscale on OpenWrt: reach Home Assistant from anywhere without port forwarding

HA News · 16 Nov 2026

You want to open your Home Assistant dashboard from a hotel, from the office, or from the car, and you don't want to forward port 8123 to the internet. The clean way to do it on an OpenWrt router is Tailscale installed on the router itself, configured as a subnet router. Your phone joins your tailnet, the router advertises your home LAN's routes, and Home Assistant stays reachable at its local address without a single inbound firewall rule. This guide covers installing Tailscale on OpenWrt, advertising your subnet, the firewall situation, and what the Home Assistant Tailscale integration does and doesn't do.

What Tailscale does on a router

Tailscale is a VPN built on WireGuard. Per Home Assistant's Tailscale integration documentation, it "creates secure connections between your devices using WireGuard". Same cryptography as plain WireGuard, which we cover in our OpenWrt WireGuard guide, but with the parts that make WireGuard fiddly automated: key management, NAT traversal, and a coordination server that hands out addresses. You don't distribute keys manually, and you don't need to listen on a port at your house.

Putting it on the router rather than on the Home Assistant machine has one practical advantage: the whole LAN becomes reachable, not just Home Assistant. Your OpenWrt router runs the Tailscale daemon on boot, advertises the LAN subnet to your tailnet, and from anywhere your phone or laptop can reach any device on your home network — Home Assistant, a printer, a camera, an ESP32 flashing host. Nothing is installed on Home Assistant or the devices themselves.

There's a trade-off to know up front: Tailscale's coordination runs Tailscale the company's servers, so sign-in is a cloud account. The traffic itself is peer-to-peer and encrypted end to end with WireGuard keys that never touch the coordination server, and if you want to self-host the coordination layer, the open-source Headscale project exists — but that's a separate build, not what this guide sets up.

Installing the package on OpenWrt

The official OpenWrt package feeds ship Tailscale. The current stable release, OpenWrt 25.12.6, includes the tailscale package — version 1.104.1 (tailscale-1.104.1-r1) appears in the official feed for aarch64_generic at downloads.openwrt.org. The oldstable release, 24.10.8, provides the package too. Check your architecture's feed on the same downloads server if you're not aarch64.

Install it over SSH:

opkg update
opkg install tailscale

One packaging note: releases from 24.10 onward switched OpenWrt from ipk to apk packaging, so on those releases the same command may be apk add tailscale depending on your setup. The package name is the same.

The tailscale package pulls in tailscaled, the daemon, plus an OpenWrt init.d service, so it starts on boot rather than living only in your SSH session. This install pattern — including the kmod-tun kernel module the daemon needs — is documented in the OpenWrt forums at forum.openwrt.org. If kmod-tun isn't pulled in automatically on your build, install it explicitly.

A note on what's official: there is no Tailscale-published OpenWrt guide. We checked the Tailscale knowledge base on 15 November 2026 and found no OpenWrt entry in the platform install docs. The OpenWrt-specific steps below are sourced to the OpenWrt package feeds and Tailscale's generic Linux and subnet-router documentation.

If you prefer a web UI, a Luci app exists as a community package — luci-app-tailscale-community (version 26.317.52279) sits in the official Luci feed for 25.12.6 at downloads.openwrt.org. It's not part of the Tailscale client or of core OpenWrt, and the command line works fine without it. Everything below uses the CLI.

Sign in and run it on boot

Once installed:

tailscale up

That prints an authentication URL. Open it in a browser, sign in to your Tailscale account (Google, Microsoft, GitHub or a plain email login work), and the router joins your tailnet. Because the init script starts the daemon at boot, the router keeps its Tailscale identity across reboots and power cuts — exactly what you want from a device that only exists to keep the tunnel up.

Make the router a subnet router

A subnet router is a Tailscale device that advertises routes to networks it can already reach — in this case, your home LAN. The steps come from Tailscale's subnet router documentation:

  1. Enable IP forwarding. In /etc/sysctl.d/99-tailscale.conf set net.ipv4.ip_forward = 1 and net.ipv6.conf.all.forwarding = 1, then run sysctl -p /etc/sysctl.d/99-tailscale.conf.
  2. Advertise your routes. Run tailscale set --advertise-routes=192.0.2.0/24, substituting your actual LAN subnet. Multiple subnets go in one comma-separated list.
  3. Approve the routes. Open the Machines page of the Tailscale admin console and approve the subnet routes for the router. Alternatively, add an autoApprovers entry to your tailnet policy file so routes from that device are approved automatically — useful if you rebuild the router often.
  4. Add an access rule. In the tailnet policy file, let your user devices reach the advertised subnet. Without this they can see the route but can't use it.
  5. Verify from another Tailscale device. From your phone on cellular data, load Home Assistant's local address. It should answer.

On a generic Linux box, steps 1 and onward are all required. On OpenWrt, the practical difference is that IP forwarding is already part of being a router — the machine has been forwarding packets since the day you flashed it — so the real work is running tailscale up on boot via the init script and advertising the LAN subnet. Tailscale's subnet-router steps then apply unchanged.

Firewall: what you do not have to open

This is the part worth underlining. You do not need to open any port forwarding. Tailscale's firewall documentation states plainly: "Most of the time, you don't need to open any firewall ports for Tailscale." Coordination happens outbound over HTTPS, and NAT traversal — punching through both routers from the inside — establishes a direct WireGuard tunnel without manual intervention. The page was last validated 2 February 2026.

Two caveats in that same documentation matter on a home router:

  • Outbound-only allowances help direct connections. If your OpenWrt firewall is unusually strict about outbound traffic, Tailscale lists what it needs to talk to: TCP port 443 (coordination and DERP relays), UDP source port 41641 to anything (direct WireGuard on its default port), UDP 3478 (STUN), and TCP 80 as a coordination fallback. Most OpenWrt setups allow outbound traffic by default, so most setups change nothing.
  • Relays are the fallback, and they're slower. If NAT traversal fails — some carrier-grade NATs and strict corporate networks cause this — traffic still flows, but through Tailscale's DERP relays rather than a direct tunnel. Encrypted either way, just with extra latency. You'll notice it as a sluggish dashboard, not a broken one.

Because the tunnel is inbound-initiated from your phone outward, Home Assistant's port 8123 never faces the internet. We explain why that port matters in its own right elsewhere in the paper; the short version is that with a subnet router, 8123 stays a LAN-only port and remote access happens over the tailnet instead.

What the Home Assistant Tailscale integration actually does

Home Assistant ships an official Tailscale integration, and it's easy to assume it provides the remote access. It doesn't. The integration is a monitor: it shows each tailnet device's last-seen time, Tailscale IP address, key expiry, and whether a client update is available, and it can notify you. The documentation's own "Important" note is worth quoting exactly: "This integration monitors your Tailscale network. It does not make Home Assistant itself reachable over Tailscale."

The docs page sits under Home Assistant 2026.11.1, so the integration is current as of November 2026. Install it if you want to watch key expiry — a client whose key expires can silently drop off the tailnet — but the thing that makes your dashboard reachable from the road is the subnet router on the OpenWrt router. One without the other leads to the common confusion: the integration appears healthy, remote access still doesn't work, because nothing is advertising routes.

Subnet routes vs exit nodes

Tailscale distinguishes two ways to expose "everything at home". Advertising 192.0.2.0/24-style subnets gives your tailnet devices access to specific LAN ranges. Advertising 0.0.0.0/0 and ::/0 — default routes — is a different feature, exit nodes, which route all of a client's traffic through your home. Per Tailscale's documentation, "If you'd like to expose default routes (0.0.0.0/0 and ::/0), consider using exit nodes instead" and use --advertise-exit-node.

For reaching Home Assistant, a plain subnet route is the right tool: it's scoped, it doesn't drag your work laptop's traffic through your home connection, and it doesn't break streaming services that dislike your home IP as a travel origin. Use an exit node only when the goal is genuinely "treat me as if I were at home for everything".

Tailscale vs plain WireGuard on OpenWrt

Both use WireGuard cryptography, so the encryption is equivalent. The differences are operational. Plain WireGuard on OpenWrt, as covered in our WireGuard guide, means generating and distributing a key pair per device, opening a UDP listening port on your home firewall for each peer, and having no coordination if your home IP changes.

Tailscale adds the coordination server, NAT traversal, and a policy file for access control — no manually distributed keys and no listening port on the home router. The cost is the cloud dependency for sign-in and coordination. If you already run plain WireGuard and your WAN IP is stable, it works well and stays entirely self-hosted. If devices wander between networks with unpredictable NATs — phones on cellular, laptops on hotel Wi-Fi — the NAT traversal and auto key handling are what you're paying for. Tailscale's own firewall documentation frames it as the difference between needing an inbound port and needing none.

Gotchas worth knowing

  • The HA integration is not the access path. Restating the docs: it monitors, it doesn't expose. The subnet router does the exposing.
  • There's no official Tailscale OpenWrt guide. Lean on the OpenWrt package feed listing and Tailscale's generic Linux/subnet router docs; anything claiming a vendor OpenWrt walkthrough is off-base as of our 15 November 2026 check.
  • Packaging changed at 24.10. OpenWrt moved from ipk to apk packaging with the 24.10 series, so older forum posts may show ipk-era commands. The package name tailscale is unchanged.
  • The Luci app is community work. luci-app-tailscale-community lives in the official Luci feed, but it's not maintained by Tailscale. It won't exist on all releases, and CLI fluency ages better.
  • Key expiry notifications are worth having. The integration can notify before a key expires; a silently expired key looks like "the tunnel broke" with no error.
  • DERP relay fallback is slow but present. A dashboard that loads in five seconds instead of one usually means NAT traversal failed, not that something is broken. Check the admin console for a direct vs relayed connection.

Where this sits in an OpenWrt house

Remote access is one of the quieter reasons to run OpenWrt. The same router that segments your IoT devices into a VLAN can host the tunnel you use to reach them from anywhere — and if you're choosing the router itself, our OpenWrt pillar and the broader WireGuard on OpenWrt guide cover the rest of the stack. FAQ

Does Tailscale on OpenWrt replace port forwarding for Home Assistant?

Yes. Tailscale builds a WireGuard-based mesh network between your devices using NAT traversal, so Home Assistant's port 8123 stays LAN-only and you reach it over the tailnet instead of exposing it to the internet.

Can I install Tailscale on any OpenWrt router?

Any router with enough storage and RAM for the tailscale package. The stable OpenWrt 25.12.6 feed ships tailscale 1.104.1 for common architectures, installed with opkg (or apk on 24.10 and newer releases, which use apk packaging).

Do I need to keep the Tailscale integration in Home Assistant for remote access?

No. The integration only monitors the tailnet; per Home Assistant's documentation, it does not make Home Assistant itself reachable over Tailscale. Remote access comes from a subnet router advertising your LAN routes, which can be your OpenWrt router.

Is the Luci app for Tailscale official?

No. luci-app-tailscale-community is a community package published in the official Luci feed for OpenWrt 25.12.6, but it is not part of the Tailscale client or core OpenWrt. The command-line client works without it.

What ports do I have to open on my OpenWrt firewall for Tailscale?

None inbound. Per Tailscale's firewall documentation, most of the time you don't need to open any firewall ports; NAT traversal handles direct connections. Optional outbound allowances (TCP 443, UDP 41641, UDP 3478, TCP 80) help direct connections succeed.

Will Tailscale slow down my connection compared to plain WireGuard?

Not when a direct connection is established; it uses the same WireGuard cryptography. If NAT traversal fails, traffic falls back to Tailscale's DERP relays, which still encrypts everything but adds latency.

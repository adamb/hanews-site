Zigbee2MQTT with Home Assistant: setup, add-on, and ZHA vs Zigbee2MQTT

HA News · 9 Nov 2026

Zigbee2MQTT is a standalone service that turns a Zigbee coordinator into a set of Home Assistant entities over MQTT. It runs next to Home Assistant rather than inside it, and every sensor, bulb and switch shows up as an MQTT-discovered entity without a vendor bridge in the loop. Setting up Zigbee2MQTT with Home Assistant takes three parts: a Zigbee adapter, a machine to run the service, and an MQTT broker — Mosquitto is the broker the project recommends, though others work. On Home Assistant OS or a Supervised install, the easiest route is the official Zigbee2MQTT add-on, which bundles the service and a broker-facing config in one place.

The other question people bring to this page is ZHA vs Zigbee2MQTT. ZHA is Home Assistant's built-in Zigbee gateway: hardware-independent, connects devices straight through a coordinator, and needs no MQTT broker in the path. Zigbee2MQTT is a separate project with its own device handling and its own configuration. Both are local; neither needs a cloud account. The rest of this guide covers what each install path requires, how discovery works, coordinators that are actually supported, and the gotchas the projects themselves document.

What you need before you start

Zigbee2MQTT's getting-started page lists three requirements:

  • A Zigbee adapter — USB, GPIO, or a remote adapter over Wi-Fi or Ethernet. The radio becomes your network's coordinator.
  • A host to run the service — a Raspberry Pi, NUC, Linux box, Windows or macOS machine all qualify.
  • An MQTT broker — Mosquitto is recommended; other brokers work.

That adapter is the part worth choosing carefully, because it holds your whole Zigbee network. Adapters must be flashed with coordinator firmware before use, though some ship pre-flashed from the factory. If you have not bought a radio yet, read our guide to choosing a Zigbee hub for Home Assistant first — it covers the same coordinator question from the ZHA side, and the hardware overlap between the two integrations is exactly why people end up on this page.

ZHA vs Zigbee2MQTT

Both integrations talk to the same coordinator; the difference is what sits between the radio and Home Assistant.

ZHA is built into Home Assistant. Per the integration's own documentation, it is a hardware-independent Zigbee gateway: devices connect directly to Home Assistant through a coordinator, with no MQTT broker anywhere in the path. It supports a wide set of device types — alarm control panel, binary sensor, button, climate (beta), cover, light, lock, number, select, sensor, siren, switch, valve and update — and its docs cover channel choice, OTA updates, groups and binding, and migrating to a new adapter.

Zigbee2MQTT is a separate service that publishes device state and commands to an MQTT broker, and Home Assistant picks entities up from there through MQTT discovery. That extra hop is also where some of its flexibility comes from: the service's device database and exposure handling are its own, not Home Assistant's.

Practical framing: if you want the fewest moving parts on a Home Assistant OS box, ZHA with a supported coordinator is the shorter path. If you want the service-side features Zigbee2MQTT is known for — or you already run an MQTT broker for other things — the add-on is a clean install. Not sure Zigbee is even the right radio for your house? We compare the options in Zigbee vs Z-Wave and Zigbee vs Thread. Switching integration later is not a lifetime commitment in either direction, but see the re-pairing note near the end of this page before you move.

Install path 1: the Home Assistant add-on

On Home Assistant OS or a Supervised install, the project's documentation calls the Zigbee2MQTT add-on the easiest route. Two hardware constraints from the add-on's own page are worth checking before you spend an evening on it:

  • 64-bit only. The add-on supports aarch64 and amd64 architectures. 32-bit boards — the docs name the Sonoff iHost and armv7 Raspberry Pi hardware — cannot run it.
  • Raspberry Pi limits. A Raspberry Pi 3 may be unstable because of limited resources; the docs say use at least a Raspberry Pi 4.

If neither applies to your box, add the add-on from Settings, then Add-ons, then the add-on store, point it at your coordinator's serial path, and let it start. The service then needs a broker to talk to — many add-on installs pair it with the Mosquitto broker add-on on the same machine.

Install path 2: standalone (Docker, Linux, everything else)

The documented install list is longer than people expect: Linux, Docker, the Home Assistant add-on, openHABian, Windows, a FreeBSD jail, and Kubernetes. If Home Assistant itself runs in Docker on a NUC, running Zigbee2MQTT as a neighbouring container is the common pattern — same host, two containers, one MQTT broker between them.

One routing note from the docs: while Home Assistant is the most common companion, Zigbee2MQTT is not Home Assistant-specific. The same service feeds openHAB or any other MQTT consumer if your setup changes later.

Turning on Home Assistant discovery

Out of the box, Zigbee2MQTT does not announce your devices to Home Assistant. Discovery is off by default; you switch it on in configuration.yaml:

homeassistant:
  enabled: true

That one block does the work, but it has documented details worth knowing:

  • discovery_topic defaults to homeassistant, and the docs warn it must differ from your MQTT base topic — if you customized the base topic, check this.
  • status_topic defaults to homeassistant/status.
  • An experimental experimental_event_entities option exists, as does a legacy_action_sensor option (default false) for the old sensor_action entity.

On the Home Assistant side, add the MQTT integration through Settings, then Devices & services, then Add Integration, then MQTT. From there entities arrive via MQTT discovery, which is the path Zigbee2MQTT uses, or manually through YAML or subentries. MQTT platforms cover lights, switches, sensors, climate, covers, locks, fans, numbers, selects, valves and more.

Picking a coordinator Zigbee2MQTT actually supports

Zigbee2MQTT groups its officially supported adapters, and the getting-started page narrows the recommendation to two chip families:

  • Texas Instruments zStack — CC2652 and CC1352 parts. Chip detail worth knowing when comparing listings: TI parts whose model number ends in P carry a power amplifier rated up to 20 dBm, versus 5 dBm on non-P variants.
  • Silicon Labs EmberZNet — EFR32-based adapters.

Adapters from the deCONZ family (Dresden Elektronik) are also in the project's supported list. The remaining groups are graded lower: not recommended, not maintained, ZiGate, and experimental ZBOSS (Nordic).

Named dongles in these families that come up constantly in the Zigbee2MQTT world include the SONOFF Zigbee 3.0 USB Dongle Plus (ZBDongle-E, EFR32MG21), the SMLIGHT SLZB-07 (also EFR32MG21), the Dresden Elektronik ConBee III, and TI CC2652P/CC1352P sticks flashed with Z-Stack coordinator firmware. SONOFF ZBDongle-E on Amazon · SMLIGHT SLZB-07 on Amazon · ConBee III on Amazon · TI CC2652P adapters on Amazon. Home Assistant's official Connect ZBT-2 also works with Zigbee2MQTT — the hub guide covers it in detail.

Whichever stick you land on, keep it off Wi-Fi. The adapter documentation warns that Wi-Fi-connected network adapters "might have reduced stability" because the serial protocol has little fault tolerance for packet loss and latency. If the radio cannot sit next to the host, the docs recommend a remote adapter over wired Ethernet instead.

Pairing devices

Zigbee devices join only when the network permits joining. In the Zigbee2MQTT frontend, the joining button — top-right of the nav bar — opens the network for 254 seconds, and you can close it early when the sensor has paired. Pair your mains-powered devices first (plugs, bulbs); they become routers that widen the mesh, then battery sensors find a better parent.

One documented trick: the arrow beside "Permit join (All)" lets you permit joining through a specific coordinator or router. That is useful when a device picks a bad parent — the docs name Aqara devices as the classic example. The caveat is real, though: permitting join through a particular router does not guarantee the device actually keeps that router as its parent.

Gotchas the docs call out

Range and stability trouble has a documented first response: move the coordinator away from the host with a USB extension cable. Keep the docs' "Improve network range and stability" page bookmarked; it is the project's own troubleshooting ladder, and the USB extension tip is the first rung for a reason — USB 3 ports and case internals are noisy neighbours for a 2.4 GHz radio.

The second gotcha is migration. Zigbee2MQTT's adapter page notes that migrating to a different adapter may require re-pairing all devices in some cases. That matters in two directions: moving from ZHA to Zigbee2MQTT usually means re-pairing onto the new service's network, and swapping coordinators later may mean re-pairing again. Budget an afternoon, or pick the adapter you intend to keep for years and don't move.

Third: the broker is load-bearing. If MQTT goes down, Zigbee2MQTT still runs but Home Assistant sees nothing. When "all my Zigbee sensors vanished," check the broker before the radio.

FAQ

Do I need a separate Zigbee hub if I already run Home Assistant?

No vendor hub. You need a Zigbee coordinator adapter plugged into a machine you control, plus (for Zigbee2MQTT) an MQTT broker. Zigbee2MQTT lists the three requirements as a Zigbee adapter, a host to run the service, and an MQTT broker.

ZHA vs Zigbee2MQTT: which should I pick for a Home Assistant install?

ZHA is Home Assistant's built-in Zigbee gateway and needs no MQTT broker in the path. Zigbee2MQTT is a separate service that publishes devices over MQTT and typically reaches Home Assistant through discovery. Pick ZHA for the simplest single-install setup; pick Zigbee2MQTT if you want the service's device handling and its adapter and device coverage.

Which Zigbee coordinator should I buy for Zigbee2MQTT?

Zigbee2MQTT's own getting-started page recommends adapters from two families: Texas Instruments zStack (CC2652/CC1352) and Silicon Labs EmberZNet (EFR32). deCONZ adapters from Dresden Elektronik are also in its supported list. The adapter must be flashed with coordinator firmware, though some ship pre-flashed.

Does Zigbee2MQTT need MQTT, and do I have to install Mosquitto?

Yes, Zigbee2MQTT needs an MQTT broker. Mosquitto is the recommended broker but others work. In Home Assistant you add the MQTT integration under Settings, then Devices & services, then Add Integration, then MQTT.

Can I run Zigbee2MQTT as a Home Assistant add-on, and what hardware does it need?

Yes. On Home Assistant OS or a Supervised install the project calls the add-on the easiest route. It is 64-bit only (aarch64 or amd64), so 32-bit boards such as armv7 Raspberry Pi hardware cannot run it, and the docs say a Raspberry Pi 3 may be unstable — at least a Raspberry Pi 4.

Can I move my devices from ZHA to Zigbee2MQTT without re-pairing everything?

Not always. Zigbee2MQTT's adapter documentation notes that migrating to a different adapter may require re-pairing all devices in some cases, so plan the move when you have time to re-pair.

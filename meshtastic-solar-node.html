Meshtastic solar node: build a solar repeater for a rural property

HA News · 14 Nov 2026

A Meshtastic solar node is a small, panel-charged radio that sits on a post, roof or tree line and rebroadcasts mesh traffic for a property too big for one node to cover. It is the classic answer to a rural question: the gate is a kilometre from the house, the mesh dies in the valley in between, and nobody wants to trench Ethernet. The short version: build it on an nRF52-based board such as the RAK WisBlock RAK4631, set it to the ROUTER role (the old REPEATER role is deprecated), enable Power Saving, match the region and modem preset of the rest of the mesh, and budget the panel and battery for the cloudy week. Here are the parts, the settings, and the gotchas.

What a solar Meshtastic node actually does

Meshtastic is a LoRa mesh: each node forwards other nodes' packets so the network spans further than any pair of radios could alone. A solar node exists purely to extend that reach across a property — it relays traffic between the gate, the water tank, the shed and whatever node is near the house. Unlike the handheld and starter picks in best Meshtastic devices, a solar node is infrastructure. Nobody holds it. It sits outdoors, permanently, on power it generates itself.

That changes what matters in the hardware. Battery life is no longer a spec sheet promise; it is your engineering problem. Idle current — what the board draws hour after hour while waiting for packets — dominates the power budget. And because the node lives on a pole, you care about how firmware behaves when the sun does not show up for a week, and how you update it without climbing a ladder. If you are comparing Meshtastic against LoRaWAN for the same job, see LoRaWAN gateways and our Meshtastic vs MeshCore comparison.

Pick the board: nRF52 for solar, ESP32 when you want Wi-Fi

The single biggest hardware decision is the microcontroller family, because it decides the idle draw. ESP32 boards ship with Wi-Fi and Bluetooth radios and idle at meaningfully higher current than nRF52 boards, even when the radios are off. On mains power nobody notices; on a solar node, the whole panel is sized off that number.

The Meshtastic device documentation points to the RAK WisBlock RAK4631 core module as the low-power path: an nRF52840 MCU paired with an SX1262 LoRa radio, no Wi-Fi on board, Bluetooth 5.0, with an optional GPS module. RAK and the Meshtastic docs describe it as low-power and solar ready — the docs literally sell the RAK4631 + RAK19007 WisBlock starter kit for this purpose.

Check the RAK WisBlock RAK4631 starter kit on Amazon for current price and stock.

The alternatives, per the Meshtastic RAK and Heltec device pages:

  • RAK11200 — ESP32 core with a radio add-on. This is the choice when the node also needs Wi-Fi, e.g. to report over the network instead of purely relaying. Higher idle draw than the RAK4631.
  • RAK11310 — RP2040 + SX1262, no Wi-Fi and no Bluetooth. Low power, but no BLE means phone setup is more awkward than on the nRF52 core.
  • RAK3312 — ESP32-S3 + SX1262 with Wi-Fi, for builds that want the compute.
  • Heltec LoRa32 V3/V4 family — ESP32-S3 + SX1262, Wi-Fi 2.4 GHz b/g/n, Bluetooth 5.0, optional GPS. Cheap and popular, but the docs' point stands: ESP32 boards idle at higher current than nRF52. Check the Heltec LoRa32 V3 on Amazon if you accept the power trade for the price.

LILYGO's T-Beam and T-Echo are also on the support list; if you build around one, verify the exact variant against the LILYGO page on meshtastic.org before ordering, since revisions differ.

For a dedicated solar repeater the RAK4631 is the default answer: lowest idle draw, BLE for setup and diagnostics, no Wi-Fi radio burning margin. You buy the starter kit, add a solar charger board and a LiFePO4 or Li-ion cell, and the node firmware is Meshtastic's own.

The role: ROUTER, not REPEATER

Here is the setting that most older guides get wrong. The REPEATER device role is deprecated as of firmware 2.7.11. It used to be the "set and forget" role — rebroadcast every packet once with minimal overhead, invisible in the Nodes list. Its visible replacement is ROUTER: it also rebroadcasts packets once, but it appears in the network topology, and on ESP32 boards it enables Power Saving mode by default.

The docs also define ROUTER_LATE, which rebroadcasts after the other roles do, deliberately late. Per the device configuration docs, ROUTER_LATE is for nodes bridging local dead spots — the valley node on your fence line is exactly that. If your repeater's job is to fill one dead pocket rather than be the mesh backbone, try ROUTER_LATE before assuming you need a taller mast.

Two ROUTER consequences to know before you set it:

  • ROUTER disables Bluetooth, Wi-Fi, Serial and the screen by default — fine, even ideal, on a node you will never touch. But it also means the phone app cannot talk to the node until you do something about it.
  • Updating a ROUTER node is done via the admin channel. The documented procedure: temporarily change the role, do the update, then revert. Factor this into your first build — you want the admin channel keys sorted before the node goes up the tower.

Source: the Meshtastic device configuration docs.

Power Saving and the cloudy-week plan

Power Saving mode disables Bluetooth, Serial, Wi-Fi and the screen to conserve power. The power configuration docs call it "particularly beneficial for devices relying on low-current power sources, like solar panels" — which is your node. On a solar build this should almost always be on, and ROUTER enables it by default on ESP32 boards.

The cost is convenience: with Power Saving on, settings changes require waking the device — user button, reset, or remote admin from another node's admin channel. On a pole-mounted node, the button and the reset button are both a ladder trip away. So the practical pattern is: configure everything thoroughly at the bench, enable Power Saving last, and make sure the admin channel works from the house before the node leaves your hands. Source: the power configuration docs.

For the cloudy week, the relevant setting is Shutdown after losing power: when external power is lost, the device shuts itself down after a defined period instead of deep-discharging the battery. That protects the cell (Li-ion cells do not like being held at zero) and keeps the node from broadcasting increasingly degraded packets for days. But the docs flag a real trap: the shutdown only happens if the board correctly detects external power — verify it via the plug icon in the app before you trust the feature. Some boards report the wrong voltage until the ADC Multiplier Override is corrected; the docs describe correcting it to a float between 2 and 6, with the example 3.20 for a divider of R1=100k / R2=220k. Get the battery gauge right first, or both the charge-state display and the shutdown logic are running on fiction.

Region and modem preset: why your node ignores the mesh

Two settings decide whether a solar repeater actually joins the mesh at all. All nodes on a mesh must share identical Region and identical Modem Preset (or identical custom modem settings) to hear each other. Per the LoRa configuration docs:

  • A node with no region set does not transmit at all. If your new repeater sits silent, check the region first — it is the most common cause.
  • The default preset is LONG_FAST, the strong mix of speed and range. But a node in the US that is first configured from its own on-device screen starts on LONG_TURBO, which cannot interoperate with LONG_FAST. So a fresh node set up at the bench while staring at its OLED may join nothing, purely because of preset mismatch.
  • Not every preset is legal in every band; the node only accepts presets the selected region permits.

Source: the LoRa configuration docs.

The bench procedure: flash the RAK4631, connect over BLE (the nRF52 core has Bluetooth 5.0), set the same region your existing nodes use, set the modem preset to whatever the mesh runs — LONG_FAST unless you deliberately chose otherwise — set the role to ROUTER (or ROUTER_LATE for a dead-spot filler), confirm the plug icon shows correct external power detection, enable Power Saving, then test the admin channel from a second node before mounting.

Power budget and enclosure, in brief terms

The docs do not give a one-line panel recommendation, so this section is method, not numbers. The budget always follows the same five lines:

  1. Measure or find the board's average idle draw — this is the dominant term for an nRF52 ROUTER node, and the reason ESP32 solar builds need proportionally bigger panels.
  2. Assume the node relays occasionally and transmit bursts add on top; a repeater in a busy mesh transmits more than a leaf node.
  3. Derive daily energy, then size the battery for days of autonomy, not one dark day — clouds cluster. LiFePO4 is the usual choice for outdoor cycled cells because of its cycle life and temperature tolerance.
  4. Size the solar panel for the worst month of sun at your latitude, not the annual average, and derate for the enclosure's mounting angle and heat.
  5. Verify wiring losses and the solar charger's quiescent draw; a charger that burns more in standby than a small panel harvests in winter is a real failure mode.

The enclosure needs UV-stable material or a shielded mount, cable glands with strain relief, the antenna external (an antenna inside a metal box is a physics problem, not a firmware problem), and the panel angled for drainage. Match the whole assembly against what you verify in the app before mounting: the external-power plug icon, the corrected battery gauge, and an admin-channel ping that gets an answer.

Placement beats power

A solar repeater's placement is decided by radio first and sunlight second, in that order, and the two often fight — the sunniest exposed location is usually also the best radio spot, which is why the combination works so well on ridgelines. Put the node where it can hear both sides: the dead-spot filler should sit roughly between the endpoints it joins, with line of sight where terrain allows. Then confirm placement with the app's node list rather than faith — a ROUTER node is visible in the topology, so after mounting, check that the house-side and gate-side nodes both see it and that traffic actually hops through it.

One habit worth adopting: leave headroom. A node placed "just good enough" on a clear day loses its margin the first time foliage fills in or a shed goes up. If the topology shows the repeater hearing its neighbours weakly, a second mount height or 10 metres of lateral move usually changes more than any firmware setting.

FAQ

Do I still use the REPEATER role on a solar node?

No — it is deprecated as of firmware 2.7.11. Use ROUTER, which rebroadcasts once and shows up in the topology, or ROUTER_LATE, which rebroadcasts after other modes and suits local dead spots.

Which board draws the least power for a solar node?

nRF52-based boards such as the RAK WisBlock RAK4631 idle at lower current than ESP32-based boards like the Heltec LoRa32 V3/V4. The Meshtastic device docs describe the RAK4631 as low-power and solar ready.

Why won't my solar repeater join the mesh?

Usually the region was never set, so the node transmits nothing at all, or the modem preset mismatches the rest of the mesh. A US node first set from its own screen starts on LONG_TURBO, which cannot interoperate with the default LONG_FAST.

How do I keep settings changes possible with Power Saving on?

Power Saving disables Bluetooth, Serial, Wi-Fi and the screen. Wake the device with its user button or a reset, use the admin channel for remote admin from another node, or temporarily change the role so the node has a live interface.

Why does my battery gauge read wrong on solar power?

The board estimates battery voltage through its voltage divider, and the default ADC multiplier may not match the board. Correct the ADC Multiplier Override for the divider (the docs give 3.20 as the example for R1=100k / R2=220k), then verify external power detection via the plug icon in the app.

What happens after several cloudy days?

When external power is lost, the Shutdown after losing power setting shuts the device down automatically after the defined period instead of deep-discharging the battery — but only if the board correctly detects external power, so verify that first.
